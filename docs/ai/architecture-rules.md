# AI 架构与模块化规则

## 核心目标

本项目要求 AI 以长期可维护为第一优先级。实现功能时，不允许为了快速完成而堆叠临时代码、重复逻辑、隐式耦合或巨型文件。

代码应该让后续开发者一眼看出：模块边界在哪里、数据如何流动、业务规则属于哪里、外部依赖被隔离在哪里。

## 执行前必须先理解

在修改代码前，先完成以下动作：

- 阅读与任务直接相关的现有文件。
- 搜索是否已有相似功能、工具函数、组件、服务或数据模型。
- 判断当前任务属于哪个模块、层级或业务领域。
- 如果已有项目模式，优先沿用；不要发明平行结构。
- 如果需求会影响多个模块，先说明拆分方案，再实施。

## 模块拆分原则

- 一个模块只表达一个清晰概念。
- 一个文件只承担一个主要职责。
- 一个函数只做一件事，并保持输入输出清晰。
- 不要把解析、校验、业务规则、数据访问、UI 渲染、流程编排混在一起。
- 当代码开始需要滚动很多屏才能理解时，应优先拆分。
- 拆分应按职责拆，不按“看起来方便”拆。
- 新模块必须有明确归属：属于业务、基础设施、UI、状态、工具、适配器还是测试。

## 架构边界

优先保持以下边界清晰：

- UI 层：只负责展示、交互和轻量状态，不承载核心业务规则。
- 业务层：放领域规则、用例流程、权限判断、核心计算。
- 数据层：负责 API、数据库、本地存储、第三方服务访问。
- 适配层：隔离外部 SDK、平台 API、框架细节。
- 工具层：只放纯函数或通用能力，不放业务分支。

禁止跨层偷懒调用。例如 UI 不应直接拼复杂业务规则，业务层不应依赖具体 UI 组件，通用工具不应反向依赖业务模块。

## 设计模式使用规则

设计模式是工具，不是装饰。只有在能降低复杂度时才使用。

优先使用：

- 组合优于继承。
- 依赖倒置：核心逻辑依赖接口或抽象契约，不直接依赖外部实现。
- 单一职责：类、函数、模块都只承担一个稳定责任。
- 策略模式：当存在多种可替换算法、规则或行为时使用。
- 适配器模式：接入第三方 API、SDK、平台能力时使用。
- 工厂模式：创建逻辑复杂、类型分支稳定时使用。
- 仓储模式：需要隔离业务逻辑与数据存储细节时使用。
- 门面模式：外部系统调用复杂，且需要提供稳定内部入口时使用。

避免：

- 为简单逻辑强行套模式。
- 只有一个实现时过早抽象。
- 创建万能 manager、helper、utils、service。
- 用继承层级隐藏真实逻辑。
- 用动态魔法、反射、隐式约定制造理解成本。

## 复用与抽象

- 发现重复逻辑时，先判断它们是否真的是同一概念。
- 真重复应抽成共享实现。
- 只是长得像但业务含义不同的逻辑，不要强行合并。
- 抽象必须有名字、有边界、有稳定责任。
- 不要为了“以后可能用到”提前抽象。
- 不要新增 wrapper、alias、兼容层，除非确实需要兼容旧接口。

## 命名规则

- 名称必须表达业务含义，而不是实现细节。
- 避免 `data`、`info`、`item`、`handle`、`manager`、`helper` 这类空泛命名。
- 布尔值使用明确语义，例如 `isEnabled`、`canSubmit`、`hasPermission`。
- 函数名应表达动作和结果。
- 模块名应表达它拥有的概念，而不是临时技术方案。

## 文件组织

新增文件前先确认：

- 是否已有合适目录。
- 是否已有同类模块命名方式。
- 是否应该放在当前模块内部，而不是全局目录。
- 是否真的需要新文件。

禁止把所有代码都塞进：

- `utils`
- `helpers`
- `common`
- `shared`
- `services`
- `manager`

除非项目已有明确约定，且新代码符合该目录职责。

## 变更策略

- 优先小步修改，保持行为可验证。
- 不做与任务无关的重构。
- 如果必须重构，先保证有测试或可验证路径。
- 修改公共接口时，同步更新调用方、类型、测试和文档。
- 删除旧代码时，确认没有调用方，而不是留下双路径。

## 测试与验证

完成代码后必须做至少一种验证：

- 运行相关测试。
- 运行类型检查或 lint。
- 对 UI 改动进行浏览器验证。
- 对核心业务逻辑补充或更新测试。
- 如果无法验证，必须说明原因和风险。

## AI 自检清单

提交结果前，检查：

- 是否产生了巨型文件或万能函数？
- 是否复制了已有逻辑？
- 是否绕过了现有模块边界？
- 是否把业务逻辑塞进 UI 或工具函数？
- 是否引入了不必要的抽象？
- 是否有清晰命名和稳定目录归属？
- 是否运行了相关验证？

如果一个实现需要靠长篇解释才能说明为什么这样组织，优先重新拆分代码，而不是写更多注释。
